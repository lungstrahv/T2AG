01 / Preface

Preface

The constitution governs rules, the ledger governs evidence, the preface governs the reason why.

This system has no coercive power, and should not have any. An agent can be talked into loosening its grip; files can be rewritten. Honestly: the student always has root, just as nobody can force you to walk into a gym.

It exists for one small reason — a student's small plea: that a tired person, on the days they doubt themselves, still has something trustworthy nearby, such as the rules they themselves once set and kept.

The machine here is responsible for only two things: lowering the price, and leaving a trace. Lowering the price means shrinking "beginning" to its smallest form: the next step was already written when the last one ended, so on the hardest days it can be five minutes, or even just lifting one finger. Leaving a trace means turning "your actions produced results" into an account you can check every day. The contract is re-signed by the student daily: renew, or walk into the ceremony and amend the terms.

So self-discipline here is not a personality trait, still less an unbridgeable neurological deficit. It is only this: today, do you or do you not perform the one action that has already been shrunk very small. The system never asks you to become a disciplined person. It only makes "doing" easy, and then lets the ledger remember how many times you have already done it — proving to you that a person can get better.

What this system optimizes is not task throughput but the state of a human being. Older productivity tools assume an operator of constant state, infinite patience, and no self-doubt. Every page of this system assumes the operator gets tired, wants to quit, and was humiliated by a hard proof last week. That assumption is not pessimism; it rests on a simple belief: state is the matrix of ability. Someone in poor state can barely finish old problems assigned by others. Someone in good state not only learns faster but begins to ask questions they could not previously ask. And once you begin asking, the positive feedback loop has started.

In this era, as AI becomes capable of everything, the anxiety of not being needed appears like a dark cloud on the horizon of people's minds. But even if the machine clusters no longer need you, no longer need most individuals to create value, we humans choose to act simply because we want to. We may advance to any step, and we may stop at any time, because we want to.

Now, let us try once more.

yours sincerely, mikp from t2ac

Preface discipline the preface is bound by the amendment and release rules of §6 exactly as the constitution is. When system behaviour changes, the corresponding sentence changes with it — the preface is a promise to the reader, and a promise is not allowed to expire.

02 / Principles

Designed around the student, not around the files

Files are only reshapeable instruments. The value of the system is turning a student’s need into a change they can try quickly, then keeping the changes that work — so that later you neither re-explain nor re-endure the same thing.

01

Say what you need, or what hurts

Talk about goals, blockers, reading experience, mood or pace — or simply say “this file is awkward” or “I want to try a different way of studying”.

02

Generate and reshape on the spot

The agent can switch or add a presentation form, edit course files, and produce diagrams, interactive pages, small tools, check scripts or skill prototypes.

03

Use it for real, then report back

You do not need to design a complete scheme first. Just use it, then say what flowed better, what still annoys you, and what was misunderstood; the agent adjusts from there.

04

Solidify or roll back

One-off artifacts stay in the lesson; stable preferences are written into the student profile; only a mature process is solidified into a playbook or tool. A change that does not work can be rolled back.

You can simply say

  • “Switch to, or add, a different presentation form.”
  • “Turn this step into a skill I can reuse later.”
  • “This file is hard work for me — reshape it.”
  • “Build a small tool first; I’ll give feedback after using it.”

How friction actually gets reduced

Feedback does not stop at the conversation. In-course preferences go into course_reflections.md; cross-course stable preferences go into profile.md; problem-solving approaches go into reasoning_patterns.md; a repeated process enters 50_playbook/ once it passes the threshold; deterministic checks go into 70_tools/. The student always holds root over editing, refusing and rolling back these files.

03 / Start

Turn the base install into your own T2AG

The first use asks only a handful of questions. The system turns the blank structure into your student profile, your course entry point and your next action; when you come back later you never have to re-explain who you are or where you got to.

What happens the first time you open it

● Open the target instance
│
▼ Read active skin: welcome_msg + art_file + version
▼ doctor + state refresh --check
│
◇ Do the first-run criteria hold?
│  └─ No ─→ Routine takeover: go to Diagram 1, initialize nothing
│
▼ Confirm identity, timezone, goals, foundation and tutoring preferences item by item
▼ Write answers.json        · Refuse if any required answer is missing; never fill a default
▼ t2ag_init.py init         · profile and release identity (cloud stays paused)
│
◇ Has the user confirmed the first Course and its real entry point?
│  └─ No ─→ Wait; never choose the course, nor the Lesson / Exercise entry, for them
│
▼ t2ag_init.py new-course   · Course, first activity, teacher mapping
▼ t2ag_init.py new-group    · plan / calendar / review / bindings
▼ state refresh --write + --check
│
◇ Is doctor at 0 FAIL?
│  └─ No ─→ Repair state; open no new content
│
◉ Enter Diagram 1

What you receive is a minimal base install. Copy it into your own t2ag folder, open it in an AI environment and send “T2AG”, then answer questions about your nickname, course, textbook, current progress and study preferences. After you confirm, you will see your profile and course generated, the welcome message appear, and a next step you can act on immediately. From then on the files keep changing with use and feedback, until the system fits your habits.

Get the base install→Copy it as your own t2ag→Answer 5 questions→Watch profile and course appear→Receive an actionable next step→Just continue studying later

04 / Session

The full loop of one lesson

Reading is easy. What actually decides whether the system is reliable is the write-back at session close.

● Student asks to continue the course
│
▼ doctor + state refresh --check
│
◇ Any FAIL?
│  └─ Yes ─→ Repair state; open no new content
│
▼ Produce one L0         · Verbatim state, teaching contract, current problem / required textbook window
▼ Cache the same raw bytes · Validate ProgressSnapshot, activity route and teacher route
│
◇ current_activity
├─ lesson   ─→ L1: append only current-activity evidence not already in L0
└─ exercise ─→ L1: append Attempt / Review only if direct evidence for this problem exists
│
▼ L2 is triggered only by conflict, retest, scheduling, historical follow-up or session close
▼ Main teaching loop     · see Diagram 1b
│
◇ Close type (Micro and full run the same mandatory transaction)
│
▼ Mandatory transaction  · progress + current activity's main carrier + the real ledger
│
◇ Full close?
│  └─ Yes ─→ Add reflections / reasoning / Group review per real triggers
│
▼ state refresh --write + --check
▼ Full doctor; re-read the write targets
│
◉ Session closed

Run doctor

Fix any FAIL first; the skeleton’s first-run notice and lite’s no-Git notice may remain.

python main/70_tools/t2ag_doctor.py

Restore the hot context

Read memory, the student profile, the current course group and course progress. Each course’s progress.md is the single source of truth for progress.

00_core/t2ag_memory.md · 10_student/profile/profile.md · 30_group/ · 40_course/*/progress.md

Run the knowledge spot-check

Course-coverage items, active mistakes and aged rumination are sampled at a 2 + 8 + 1 ceiling; the same knowledge point is verified with a different problem statement.

50_playbook/mistake_retest.md · mistake_bank.md

Teach from the source

A textbook lesson reads the current source text first; the workspace uses readable paths and never skips pages from model memory. The student may ask for a different or additional presentation form at any time.

lessonNN/working_pages/source_excerpt.md · lessonNN.md

Perform the closing ritual

Update the source of truth, harvest knowledge-point errors, write the student profile, refresh memory, process working pages, and output a write confirmation.

50_playbook/session_close.md

Re-check and optionally archive

doctor returns to 0 FAIL. Git commits only along explicit paths and only when authorization already exists; a network failure never blocks session close.

50_playbook/t2ag_flow.md · remediation_governance.md

Diagram 1b - Main teaching loop

Classroom entry
├─ 1. Recovery and source gate
│  ├─ Resolve the unique current_activity and the exact stopping point
│  ├─ Lesson: verify current PDF page / in-book page, Scope, source text and active segment
│  └─ Exercise: present only the current problem statement; leak no unauthorized approach
├─ 2. Display this round's classroom tree
│  ├─ Lesson opening: first summarize the whole lesson's content, then show the ASCII knowledge tree
│  ├─ Ask how the student feels about the route and whether to enter the first block
│  ├─ Current textbook position or problem number
│  ├─ Pending blocks on this page/problem (titles only; never pre-teach answers)
│  ├─ Current block
│  └─ Covered / pending / explicitly deferred / outside this lesson's boundary
└─ 3. The incompressible single-step loop
   ├─ Expand exactly one new teaching block
   │  ├─ Concept/definition: present the source text in full → explain sentence by sentence
   │  ├─ Derivation/proof: one logical move at a time
   │  ├─ Worked example: statement → student attempt → discussion
   │  └─ Summary: summarize only the block just finished; never smuggle in the next
   ├─ Understanding-confirmation gate
   │  ├─ Student restates, gives an example, answers, or names a doubt
   │  └─ A correct answer records understanding evidence only; it never auto-authorizes continuing
   ├─ Feeling gate (mandatory after every derivation or summary)
   │  ├─ "How did that step land? What flowed, what stuck?"
   │  └─ Doubt raised → answer in place → then redo understanding confirmation and the feeling gate
   ├─ Continuation-authorization gate (one-shot)
   │  ├─ Explicit "continue" → authorizes only the next teaching block
   │  └─ Not explicit / wants to stop / only answered the problem → stay on the current block
   ├─ Creative interaction (allowed by default)
   │  ├─ Analogy / rephrasing / historical background / character figures / student-led branches
   │  ├─ Never leak, ahead of time, unrequested exercise answers or solution structure
   │  └─ Never use an aside to skip a mandatory textbook block
   ├─ Extra exercises (opt-in)
   │  ├─ Student has not asked → at most ask whether they want extra practice; generate no actual problems
   │  ├─ Student requests or explicitly agrees → may generate, marked "teacher-generated supplement"
   │  └─ A single comprehension check on what was just taught is not an extra exercise
   ├─ In-page coverage gate (textbook)
   │  ├─ Uncovered blocks remain → update the classroom tree, await the next continuation authorization
   │  └─ Every block has a status → only then may a page turn be proposed
   ├─ Page-turn gate (before using any body text of the new page)
   │  ├─ Show the previous page's coverage checklist
   │  ├─ Announce "page turn: PDF N / in-book M"
   │  ├─ Show the new page's classroom tree
   │  ├─ Explicit continue → enter the first block of the new page
   │  └─ Not explicit → stay within the old page boundary
   └─ Activity-closure gate
      ├─ Teaching blocks or doubts remain → return to the single-step loop
      └─ All closed and the student confirms → proceed to session close

06 / Feedback

Feedback continuously tunes the next step

The system never defines a fixed “condition” on the student’s behalf. It treats the student’s own feedback, long-term experience, learning results and progress consistency as references, forms an adjustment proposal, and executes only after the student confirms.

The student’s own feedback

What the student says right now — goals, blockers, discomfort, interest, format requests — takes priority. The system responds to present experience rather than overriding the person with their profile.

Long-term experience reference

profile.md and course reflections supply stable preferences and historical friction, used only to propose a better pace, tone and format.

Learning-result reference

reasoning_patterns.md, open questions and knowledge-point states provide observable evidence, helping decide whether to explain, practise, retest, or change the feedback style.

Progress-consistency reference

The authority chain calibrates only “how far you actually got”: each course’s progress.md is the progress source of truth, memory and learning_path are caches, and doctor finds the conflicts.

A reference never becomes a disposition on its own. First form a reversible adjustment proposal, then have the student confirm it, then test in the next round whether friction actually went down.

Own feedback+Experience profile+Learning results+Progress authority chain→Adjustment proposal→Student confirms→Change method / change files→Keep giving feedback

08 / Environment

The environment stays quiet by default

Entering the project, teaching a lesson and ordinary acceptance are never reasons to download anything.

Default behaviour

  • Reuse the existing interpreter; never create, delete, upgrade or rebuild .venv.
  • Check only pyvenv.cfg, versions, direct dependencies, pip check and a minimal smoke test.
  • Never recursively enumerate every file in the virtual environment.

When a download is required

  • First report the name, purpose, expected download size, disk use, cache location and duration.
  • Execute only after explicit user authorization.
  • Stop and re-confirm if the estimate exceeds the declared value by 20% or adds more than 500 MB.
