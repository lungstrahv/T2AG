# T2AG 0.2.3 functional flow diagrams

**Protection level**: core-playbook

> This file is a derived view of `t2ag.md`, the domain model and the playbooks. It legislates nothing on its own.
> The `FLOW` markers of each diagram are extracted by the offline HTML guide generator; never delete or reuse them.

**All diagrams are character figures (```text fences).** Earlier versions allowed general system processes to use
Mermaid, hoping diagrams would track versions automatically. But a flow diagram encodes **intent**, not something
derivable from directory structure, so that benefit never materialized — the diagrams still needed hand
maintenance, and we additionally carried a home-grown SVG layout engine. Mixing two visual languages produced nine
diagrams where five looked one way and four another. They are now uniformly character figures: consistent for the
reader, readable in diff, and the offline guide needs no rendering layer. Mermaid is fine as a format; this file
just does not use it.

What can be generated from reality is left to the generator: the offline guide's **directory tree** is produced by
`build_guide.py` scanning the real filesystem, so a structural change is picked up on the next build. Flow diagrams
are not in that category — they are hand-written, and we admit they are hand-written.

Character figure notation: `●` start · `▼` action · `◇` decision · `├─ └─` branch exit · `◉` end ·
text after `·` is a supplementary note for that step.

## Diagram 0 · First run

<!-- FLOW:first_run -->
```text
● Open the target instance
│
▼ Read active skin: welcome_msg + art_file + version
▼ doctor + state refresh --check
│
◇ Do the first-run criteria hold?
│  └─ No ─→ Routine takeover: go to Diagram 1, initialize nothing
│
▼ Confirm identity, timezone, goals, foundation and tutoring preferences item by item
▼ Write answers.json        · Refuse if any required answer is missing; never fill a default
▼ t2ag_init.py init         · profile and release identity (cloud stays paused)
│
◇ Has the user confirmed the first Course and its real entry point?
│  └─ No ─→ Wait; never choose the course, nor the Lesson / Exercise entry, for them
│
▼ t2ag_init.py new-course   · Course, first activity, teacher mapping
▼ t2ag_init.py new-group    · plan / calendar / review / bindings
▼ state refresh --write + --check
│
◇ Is doctor at 0 FAIL?
│  └─ No ─→ Repair state; open no new content
│
◉ Enter Diagram 1
```
<!-- /FLOW:first_run -->

The first-run criteria are: the profile is uninitialized, required placeholders remain, or the last-lesson date in
memory is `—`.

The instance is generated by `main/70_tools/t2ag_init.py`; the model does not hand-copy files from `first_run.md`.
The model's job is to ask, write the answers into `answers.json`, call the tool and review the output. The tool
instantiates only from `40_course/_templates/` and `30_group/_templates/`, and refuses with a single complete report
if any required answer is missing. It never chooses the course or entry point, installs dependencies, creates
`.venv`, downloads textbooks, generates Engagements, performs git writes, or runs doctor and state refresh on your
behalf. All preconditions are validated before the first disk write, so a failure never leaves half a course behind.

## Diagram 1 · One teaching session

<!-- FLOW:panorama -->
```text
● Student asks to continue the course
│
▼ doctor + state refresh --check
│
◇ Any FAIL?
│  └─ Yes ─→ Repair state; open no new content
│
▼ Produce one L0         · Verbatim state, teaching contract, current problem / required textbook window
▼ Cache the same raw bytes · Validate ProgressSnapshot, activity route and teacher route
│
◇ current_activity
├─ lesson   ─→ L1: append only current-activity evidence not already in L0
└─ exercise ─→ L1: append Attempt / Review only if direct evidence for this problem exists
│
▼ L2 is triggered only by conflict, retest, scheduling, historical follow-up or session close
▼ Main teaching loop     · see Diagram 1b
│
◇ Close type (Micro and full run the same mandatory transaction)
│
▼ Mandatory transaction  · progress + current activity's main carrier + the real ledger
│
◇ Full close?
│  └─ Yes ─→ Add reflections / reasoning / Group review per real triggers
│
▼ state refresh --write + --check
▼ Full doctor; re-read the write targets
│

```
<!-- /FLOW:panorama -->

When cloud is `paused`, only the mobile projection is skipped — never the local write-back. Course progress is
written only to `progress.md`; memory and learning path are both generated by state refresh.

## Diagram 1b · Main teaching loop

<!-- FLOW:teaching_loop -->
```text
Classroom entry
├─ 1. Recovery and source gate
│  ├─ Resolve the unique current_activity and the exact stopping point
│  ├─ Lesson: verify current PDF page / in-book page, Scope, source text and active segment
│  └─ Exercise: present only the current problem statement; leak no unauthorized approach
├─ 2. Display this round's classroom tree
│  ├─ Lesson opening: first summarize the whole lesson's content, then show the ASCII knowledge tree
│  ├─ Ask how the student feels about the route and whether to enter the first block
│  ├─ Current textbook position or problem number
│  ├─ Pending blocks on this page/problem (titles only; never pre-teach answers)
│  ├─ Current block
│  └─ Covered / pending / explicitly deferred / outside this lesson's boundary
└─ 3. The incompressible single-step loop
   ├─ Expand exactly one new teaching block
   │  ├─ Concept/definition: present the source text in full → explain sentence by sentence
   │  ├─ Derivation/proof: one logical move at a time
   │  ├─ Worked example: statement → student attempt → discussion
   │  └─ Summary: summarize only the block just finished; never smuggle in the next
   ├─ Understanding-confirmation gate
   │  ├─ Student restates, gives an example, answers, or names a doubt
   │  └─ A correct answer records understanding evidence only; it never auto-authorizes continuing
   ├─ Feeling gate (mandatory after every derivation or summary)
   │  ├─ "How did that step land? What flowed, what stuck?"
   │  └─ Doubt raised → answer in place → then redo understanding confirmation and the feeling gate
   ├─ Continuation-authorization gate (one-shot)
   │  ├─ Explicit "continue" → authorizes only the next teaching block
   │  └─ Not explicit / wants to stop / only answered the problem → stay on the current block
   ├─ Creative interaction (allowed by default)
   │  ├─ Analogy / rephrasing / historical background / character figures / student-led branches
   │  ├─ Never leak, ahead of time, unrequested exercise answers or solution structure
   │  └─ Never use an aside to skip a mandatory textbook block
   ├─ Extra exercises (opt-in)
   │  ├─ Student has not asked → at most ask whether they want extra practice; generate no actual problems
   │  ├─ Student requests or explicitly agrees → may generate, marked "teacher-generated supplement"
   │  └─ A single comprehension check on what was just taught is not an extra exercise
   ├─ In-page coverage gate (textbook)
   │  ├─ Uncovered blocks remain → update the classroom tree, await the next continuation authorization
   │  └─ Every block has a status → only then may a page turn be proposed
   ├─ Page-turn gate (before using any body text of the new page)
   │  ├─ Show the previous page's coverage checklist
   │  ├─ Announce "page turn: PDF N / in-book M"
   │  ├─ Show the new page's classroom tree
   │  ├─ Explicit continue → enter the first block of the new page
   │  └─ Not explicit → stay within the old page boundary
   └─ Activity-closure gate
      ├─ Teaching blocks or doubts remain → return to the single-step loop
      └─ All closed and the student confirms → proceed to session close
```
<!-- /FLOW:teaching_loop -->

The ASCII knowledge tree must be shown together with the content overview at the start of every Lesson. The
classroom flow tree must additionally be shown at the start of a textbook Lesson, at page turns, and whenever the
student asks to see the flow. In a long lesson, update a short-form tree after the current branch changes.
Understanding confirmation, feeling feedback and continuation authorization are three distinct gates; a single
"yes", one correct answer, or a "let's study" at the start of the session must never authorize all subsequent
blocks. An unauthorized tree for a new Exercise must not leak methods or sub-goals. The opening overview and
creative warm-up count toward neither coverage nor mastery; hint strength may vary, but the correctness standard
may not.

## Diagram 6 · Git workflow

<!-- FLOW:git -->
```text
● Trigger: milestone, release or recovery
│
▼ git status --short + diff --check
│
◇ Any unexplained changes?
│  └─ Yes ─→ Handle only the explicit paths owned this round; leave the rest untouched
│
▼ Review the working-tree diff
│
◇ Release gates and independent re-review passed?
│  └─ No ─→ Creating a formal snapshot is forbidden
│
◇ Did the user explicitly authorize the commit?
│  └─ No ─→ Stay uncommitted; report truthfully
│
▼ Explicit add → cached diff → commit
│
◇ Did this batch touch Main / Skeleton shared files?
│  └─ Yes ─→ cmp for byte parity across both repos, then commit each
│
▼ sync_lite.py --write     · Regenerate only from a clean Main; a dirty tree is refused
│
◇ Need to repackage the release artifact?
│  └─ Yes ─→ Repackage at the final HEAD, excluding .git; the old package must not ship
│
◇ Need to push?
│  └─ Yes ─→ Only display the command; await separate authorization (RT3)
│
◉ Local snapshot complete
```
<!-- /FLOW:git -->

Never use `reset --hard`, `clean -fd` or force-push on your own initiative. Git is a protection layer, not the
course source of truth.

The projection directions of the three releases are asymmetric, and all come after commit:

- **Main ↔ Skeleton** is a mirror relation. Shared implementation, contracts and core/meta playbooks must be
  byte-identical; verify each with `cmp` after editing. Skeleton keeps only release-surface differences (zeroed
  instance, zeroed EV register, privacy exemptions).
- **Main → Lite** is a one-way projection. `sync_lite.py` **refuses to run** when the Main working tree is dirty —
  projecting an intermediate state that exists in no commit into a git-less Lite is unrecoverable. `--force` exists
  but is discouraged; the correct order is always commit first, then project. Lite is a read-only review snapshot;
  its acceptance is the full projection hash, and doctor is not run inside Lite.

The Git evidence boundary has three layers:

```text
evidence checkpoint ── file list / fingerprints / tests / WARN; Git not required
recovery checkpoint ── a bounded-authorization local intermediate commit; provides recovery only
release snapshot ───── the final HEAD/tree bound by full candidate re-review + finalization delta re-review
```

The three are not interchangeable: `clean ≠ reviewed ≠ released`. Authorization is still per-instance by default; a
frozen and enumerated `version_campaign` envelope may continuously cover only the limited RT1/RT2 checkpoints
within it. Push, tag, real migration apply, terminal lifecycle and other RT3 actions are never implied by an
ordinary campaign Git plan.

Bounded finalization uses a fixed sequence: operator stages an exact allowlist → an independent reviewer pre-checks
the `expected tree` → operator commits that same tree → reviewer verifies parent/tree/diff → finally an immutable
external report is produced. A PASS is never written back into the target repo or the construction report.

## Diagram 7 · Batch remediation governance

<!-- FLOW:batch -->
```text
● Register reproducible facts and the current contract
│
▼ Classify: FAIL / REVIEW / WARN / WAIVED
│
◇ Remediation needed?
│  └─ No ─→ Go straight to "record evidence"
│
├─ Remediation round (at most three substantively different attempts per round)
│  │
│  ◇ Did this round converge?
│  │  └─ Yes ─→ Exit the loop, record evidence
│  │
│  ◇ Three rounds completed?
│  ├─ No ─→ Reclassify on the new evidence ─→ back to the top of this round
│  └─ Yes ─→ Stop forcing it: separate fact, inference and requirement
│           └─→ Discuss a change or withdrawal with the requester (no further solo attempts)
│
▼ Record evidence and verification results
▼ Full gates + independent re-review
│
◇ Passed?
│  └─ No ─→ Return to remediation; severity does not auto-escalate
│
◉ Await user authorization for the snapshot
```
<!-- /FLOW:batch -->

Hard release gates cannot be waived; only external environment problems that do not affect in-repo correctness may
be recorded as a formal waiver.

Batch scheduling first selects an `execution_mode`: `independent_batch` is the default. `version_campaign` takes
effect only after the user approves an envelope containing the campaign ID, version, baseline, included/deferred
scope, repos/paths/operations, risk tier, Git plan, retained RT3 items and expiry conditions. Ordinary units run
targeted tests; RT2 risk boundaries, cross-release sync and the final candidate run the full doctor. Stop
immediately on scope expansion, an unknown repo/path, risk escalation, an unknown FAIL/WARN, or an unprovable
impact closure.

The first version candidate requires a full independent re-review. A later finding may enter delta re-review only
when the input manifest is unchanged and the impact closure is provable; the indivisible global gates must still be
re-run — doctor, state, migration, journal, Main/Skeleton parity, Lite projection and the final source fingerprint.

## Maintenance conventions

1. This file is a view; when it conflicts with an authority, fix the diagram.
2. The nine FLOW IDs must be unique and open/close paired, and are validated by doctor. Changing the ID set
   requires updating `EXPECTED_FLOWS` in `t2ag_doctor.py` in step.
3. Every FLOW block must be a ```text character figure. `build_guide.py` exits with an error on ```mermaid because
   the guide side has no rendering layer — an error beats silently producing an ugly diagram.
4. The HTML guide is generated by `build_guide.py` with no dependency on a public CDN. After editing this file you
   must run `build_guide.py --write` once in each repo, or doctor will report figure-count drift.
5. Main and Skeleton contents are identical; Lite is regenerated from Main only, and only from a clean tree.
