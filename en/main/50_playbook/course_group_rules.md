# Course identification and course-group rules (in `main/50_playbook/`)

**Protection level**: playbook

> Origin: the "current course" cache in an old instance profile once conflicted with the course-group member table (whether `planned` counted as "current" could not be adjudicated).
> This file settles the reference confusion around course identification once and for all, and freezes the operating rules of a course group.
> Where it conflicts with the t2ag.md constitution, the constitution governs; the clauses in this file are enforced by doctor.

## 1. Course lifecycle and the capacity combination

### 1.1 The course lifecycle (written at the top of each `progress.md`)

```
planned (pre-planned; exists only in a course `progress.md` or in the `plan.md` of a planned group)
  → ongoing (started and not yet finished)
  → completed (the completion criterion has closed)
  → dropped (the user ended it explicitly; the reason is kept)
```

The course lifecycle and the current course group are independent of each other. A course not in the
current group may still be `ongoing`; it may be advanced temporarily when the user asks explicitly, but it
does not thereby gain the current group's budget, and one temporary session does not automatically change
groups.

### 1.2 The current capacity combination

The `main/30_group/<GID>/plan.md` that is currently active is the **focus execution combination** the user
confirmed: its member courses receive a time budget, a minimum frequency, milestones, and project
commitments. The group file is not a list of "every course still in progress", and it is not an exclusive
lock.

- The system may propose adjustments based on actual duration, learning capacity, a failed start, a
  deadline, a dependency, or a project constraint.
- Joining, removing, or lowering frequency still requires the user's confirmation; the agent must never
  change groups on its own.
- The current capacity state is derived from the active G file and is not written back into `progress.md`:
  `focused_in_Gxx / queued_for_Gxx / unallocated`.
- The full progress-node and auto-save rules are in `50_playbook/progress_tracking.md`.

## 2. Reference discipline for course identification (the fix from this incident)

1. **The authority chain has exactly one owner**: the active group's `plan.md` is the sole source of truth
   for the current capacity combination;
   memory's "current state pointer" is only a recovery cache generated by `t2ag_state_refresh.py` and must
   never own members or budget in reverse.
   - The group-transition ritual writes the group plan first, then runs the state refresh.
   - When memory and the plan conflict, the plan governs and the GENERATED pointer is repaired.
2. **An enumerated current-capacity list is forbidden repository-wide**: the student profile, hand-written
   prose in learning_path, and any .md must never hand-write "current courses: A, B, C".
   When a reference is needed, write only a pointer, and **never hard-code the group code**:
   - ✅ `Current course group: see the memory pointer (members are in the group file)`
   - ❌ `Current course group: G01` (a copy of the group code; it rots on the next group change)
   - ✅ `Current course: IV1001 (see the group file)` (a single-course reference with a pointer; legal)
3. The course lifecycle and capacity state in `main/10_student/profile/learning_path.md` are a
   machine-generated cache:
   - The lifecycle comes from each course's `progress.md`.
   - The capacity state comes from the current active G file and the planned G files.
   - It is refreshed uniformly by `70_tools/t2ag_state_refresh.py`; hand-writing inside a generated block
     is forbidden.
4. **A law, filed permanently** (a permanent problem-log entry): any information written by hand twice will
   end up inconsistent — progress, version number, and the course list have each verified this three
   times. The remedy is always the same: delete the copy, keep the pointer.

## 3. The two-track nature of a course group (design intent, for reference when forming a group)

Each group should contain two kinds of member, in a ratio that shifts with the stage:
- **The project track** (building something external): acceptance is on the world's side — it runs, it
  produces, it can be delivered (for example PY1001+EG-0002)
- **The language track** (building internal structure): acceptance is mainly by written examination, with
  process indicators as support; problems are compiled from real past papers only and are never generated
  by AI. The body is in `main/50_playbook/exam_protocol.md`.

The language track's default final weighting: 70% written paper, 30% process indicators. The written
examination must come from an isolated assessment pool; process indicators may include the mistake_bank
recurrence rate, instant counterexample recall, blind grading, and the like.
The group file's member table gains a "Track: project / language" column, and the final evaluation accepts
each by its own standard; the two must never be converted into each other.

### The project-track verification clause

> Every milestone of a project-track course must be bound to a verification mode (A/B/B-K, registered before the group is formed or before the M starts; a major-adjustment window may change an M that has not started), and any mode must satisfy the three mechanisms: an external source of truth, an independence measurement, and a trace left by failure.
> The operational detail is in `50_playbook/project_verification.md`.

## 4. The boundary between rigid and fluid (group operating rules)

> **The execution-parameterization principle**: the protocol layer specifies only the mechanisms that must exist; it does not fix parameter values. The cycle structure, the review position, the minor-adjustment frequency, the major-adjustment frequency and the like are generated in the group-forming ritual or in the student's execution parameters; until they are discussed, the protocol defaults below apply.
>
> **The protocol default adjustment rule**: a 3-1-3 cycle; two minor adjustments per loop (at most one runtime parameter each), and one major-adjustment window every three loops.

| Dimension | Rule |
|---|---|
| Cycle | **Rigid**. The execution parameters must name the cycle container; the end-of-term node does not move back, and slippage is absorbed by the buffer or a major-adjustment window |
| Frequency red line | **Rigid**. A cycle that breaks the line counts toward the final evaluation, and two consecutive breaking cycles trigger an emergency review |
| Rituals | **Rigid**. The review, the adjustment, the written examination, the group-level evaluation and the group-closing ritual may not be skipped; their exact frequency is set by the student's execution parameters |
| Scope | **Elastic**. Content may be cut into the next group, and a cut must leave a trace (progress records "what was not finished and where it went") |
| Recipe | **Fluid between groups, frozen within one**. Adding or removing a member, changing a textbook, or promoting a course's status happens only at the group-closing ritual; inside a group, only the minor/major adjustment channels are used |

> **The adjustment-tier boundary**: a minor adjustment = a runtime parameter; a major adjustment = scope-level; recipe-level = group membership / textbook / course lifecycle, which happens only at the group-closing ritual or in a capacity reorganization the user initiates explicitly.
> The mechanical test: any adjustment that requires touching the group file's member table or a progress lifecycle field is at least a major adjustment; anything that adds or removes a course, or swaps a textbook, is recipe-level.
>
> The principle: a fixed deadline with elastic scope = the entire secret of a completion rate; changing the recipe mid-group = the study version of "losing patience and walking out during a slow decline".
> The narrative value of the first complete closed loop > any specific content inside the group — completion itself is the refutation of the old history.

## 6. The six additional doctor checks

| Check | Level |
|---|---|
| the group file the memory pointer names does not exist, or its status is not active | FAIL |
| the repository-wide count of active groups ≠ 1 | FAIL |
| a member course of the active group lacks `progress.md`, or its lifecycle is planned/completed/dropped | FAIL |
| an ongoing course outside the group is studied temporarily | PASS; no automatic group change |
| actual study departs from the capacity combination over a long period | WARN; suggest a review, no automatic group change |
| an enumerated course list appears in a .md outside the authority chain | WARN |
| a problem-number reference from an assessment-pool paper appears in a lesson/practice file | FAIL |
| a paper folder exists under `papers/` but is not registered in the index, or its meta lacks a column or the answer page numbers | WARN |
| an `ongoing` course's `course.md` has no `source_catalog:` | WARN |
| `source_catalog:` exists but `diff_recorded` will not parse | FAIL |
| `source_catalog: none` with no reason written | WARN |

> The field structure and anchor semantics of the last two, and **why a missing one is only a WARN**
> (a pre-drawing is a falsifiable prediction whose value is the diff on the round the catalogue is taken;
> judging it FAIL would trade the information away for coercion), are canonically owned by
> `doctor_contracts.md` §9 and are not copied here.

> The implementation reading of the fourth condition:
> - **Catch enumerations only; a single-course reference is legal**: match when **≥2 course codes** appear on the same line after "Current course" (counting the `[A-Z]{2,}\d{3,}` pattern); a single code does not trigger it.
> - **Allowlist**: the `plan.md` of an active/planned group (the source of truth itself) is exempt and is not disturbed by this rule.
> - A single-course reference such as `Current course: IV1001 (see the group file)` is not a violation; if that course is not in the current group's member table, doctor throws in a WARN of "stale reference".
