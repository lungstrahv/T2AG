# 整改治理规则

**保护级别**：meta-playbook

> 本规则用于缺陷修复、独立复审和发布整改。目标是区分可复现事实、模型推断与需求
> 本身，避免因模型反复失败而自动抬高严重度或硬凑修复。

## 一、问题分类

| 分类 | 判据 | 默认处置 |
|---|---|---|
| `FAIL` | 可复现、可定位，且违反明确的现行契约 | 修复；发布硬门未清零时阻断发布 |
| `REVIEW` | 需求含糊、模型判断不稳定，或存在多种合理设计 | 分离事实/推断/需求，与需求提出者讨论 |
| `WARN` | 事实成立，但不阻断当前目标 | 留证并在约定窗口处理 |
| `WAIVED` | 与需求提出者讨论后，明确延期或接受外部环境风险 | 保存批准、证据、风险和失效时间 |

`REVIEW` 不是较轻的 `FAIL`，`WAIVED` 也不是假绿。分类变化必须有新证据、契约变化
或需求提出者的明确裁决，不能只因为模型已经尝试多次。

## 二、有界整改与 campaign 止损

<!-- rule: AUTH-NONAMP-005 -->
正式 campaign 开始前必须冻结验收规范及版本、完成定义、最大整改轮数、完整复审次数，
以及测试命令数、时间与 token 预算。默认最多两轮 finding 整改和两次完整候选复审；每轮
最多三次有实质差异的尝试：

1. 第一轮仍失败时重新分类后进入第二轮。
2. 第二轮仍未收敛，或任一冻结预算先达到上限时，立即停止施工，状态记为
   `stopped_budget`，输出已有证据与未闭合项，等待需求提出者决定。
3. 不得更换 RD 编号、重冻同类 package、新建续单或拆分同一 finding 来规避上限。
4. 新增标准若揭示既有安全或核心契约违反，应停止并报告；不得自动扩张当前完成定义或
   自动生成下一轮整改。

一次有效尝试必须包含新的修改、诊断方法、证据或契约解释。对同一状态重复运行同一命令
不计作新的尝试。每轮记录假设、动作、结果和分类理由。只有需求提出者在预算耗尽后明确
批准新的有界 envelope，才可继续。

## 三、发布硬门与 waiver

以下现行契约的失败不得 waiver：

- 数据完整性或不可逆丢失风险；
- 活动入口、指针或恢复路径悬空；
- schema 与稳定 ID 冲突；
- 权威来源互相冲突；
- Main/Skeleton 契约差异超出批准分叉；
- Main → Lite 投影存在缺失、差异或孤儿。

如果需求本身不合理，可由需求提出者明确修改或撤销契约；这是需求变更，不是 waiver。

只有外部环境导致、且不影响仓内正确性的检查才可申请 `WAIVED`。正式 waiver 必须记录：

- 检查与复现证据；
- 无法在仓内修复的原因；
- 对当前发布的风险；
- 批准人和批准时间；
- 失效时间或重新验证条件。

doctor 不得把 waiver 显示为 PASS；应显示 `WARN/WAIVED`。独立复审仍可拒绝 waiver。

## 四、验收表述

- 机械检查通过，只能说明被检查的契约通过。
- `REVIEW` 未决时不得写“独立复审无阻断”。
- 发布结论必须列出仍有效的 WARN、WAIVED 和人工复审边界。
- 重试次数、模型信心或问题描述的语气不能替代证据。

## 五、版本候选与 delta re-review

### 5.1 首次候选

每个版本的首次 release candidate 必须接受完整独立复审。当前 0.2.1 没有可继承的完整
独立通过基线，不得用 finding delta 或既有实施方自检代替整版复审。

### 5.2 Delta manifest 与影响闭包

每个整改使用稳定 `D-n`，至少记录：

```text
pre/post 指纹
修改文件与允许路径
直接/间接消费者
生成物
Main/Skeleton/Lite 影响闭包
复用证据 ID、输入 manifest SHA 与新增 delta
```

同一版本内多个已列明 RT1/RT2 优化可以累计为一个 candidate delta pack，一次审查其完整
影响闭包，不按需求条数机械重复全文读仓。已经通过且指纹未变的历史范围不得因为新增普通
优化而反复全文复审。

### 5.3 不可分割全局门

delta re-review 可以只重审 finding delta，但每次都必须重新运行以下全局门：

- `t2ag_doctor.py --profile release` 与 state refresh；
- migration、journal/index 与未完成 transaction；
- Main/Skeleton 同源文件；
- Main → Lite 投影；
- 最终源、候选 tree 和输入 docs manifest 指纹。

既有报告、引用归因和测试证据只有在其输入 manifest SHA 未变时才可复用。复用时记录旧证据
ID 与新 delta，不复制全文；范围外文件指纹变化必须拒绝复用。

### 5.4 必须退回完整复审的边界

以下任一变化不能只做 delta re-review：权威链、schema、registry 生命周期、migration apply
语义、事务引擎、候选生成、安全/隐私边界，或无法证明影响闭包。此时旧 candidate 失效，
必须重新形成候选并做完整独立复审。

### 5.5 reviewer 独立性与 finalization

- delta reviewer 不得是该 delta 的 operator；可以复用上一轮独立 reviewer，但必须记录模型/
  会话、pre/post 输出、`expected tree`、staged diff SHA 和最终 attestation SHA；
- finalization 在 commit 前审查 expected tree，commit 后核对 parent/tree/diff；tree 不等、范围外
  路径、operator 自审、报告回写或提前 PASS 均拒绝；
- reviewer output 是稳定性检查完成后最后生成的不可变外部报告。PASS 不回写目标仓、施工报告
  或索引，避免“写入通过结论又制造新的未审 delta”。

### 5.6 审查成本与环境预检

- 普通版本内优化只审已证明的影响闭包并重跑 §5.3 全局门；完整 V 只针对一个冻结的 release
  candidate 执行一次。只有新 P0/P1/P2、范围扩张或无法证明影响闭包导致 candidate 失效时，
  才冻结新 candidate 并重跑完整 V；finalization 只审 §5.5 的有界 delta；
- 长测试前先验证 reviewer 可读 Main/Skeleton/Lite、report parent 可原子写入、temp-root 可完成
  一次 create/delete、脚本和 contracts 可读。权限、timeout、脚本不可读属于基础设施失败，
  不得冒充产品负例 PASS；
- LOOP 在建夹具前做单次随机 `mkdir` 写探针，每个子进程有明确 timeout，并在 stdout 之外先
  落 durable progress；同一环境边界最多一次正常尝试加一次有界诊断，前提未变化时不得重复
  空跑同一长命令；
- `.venv` 禁止作为普通审查对象递归哈希。只确认目录仍存在、`pyvenv.cfg` 与已冻结证据一致，
  且 campaign 未执行创建、删除、安装或升级命令；只有依赖变更在范围内时才检查依赖清单；
- `.recovery`、`.staging` 普通审查只确认仍存在且没有删除操作；只有 recovery/staging 功能本身
  在施工范围内时才检查内容；
- tracked 内容由 clean HEAD/tree 与 `git status` 绑定，不再重复读取大文件。真实课程证据优先
  复用已冻结 manifest；只有 path/size/mtime 或 Git blob 变化的文件才重算 SHA；
- 任何预计读取超过 100 MB 或 10,000 文件的检查，执行前必须记录现有 digest 不能复用的具体
  原因。没有该证明时拒绝自动全扫；已发生的大扫描证据不得升级为后续固定门。

## 六、取舍原则：质量优先，省成本是让步

> **优先保证质量是必须的；节省 token / 时间 / 算力是无奈之举。
> 破坏系统可靠性去换成本，任何时候都不成立。**

该原则由学生 2026-08-07 明确制定，用于裁决「更省」与「更可靠」冲突时的方向。
它是**判据**，不是态度表述——两条可直接套用的推论：

1. **误报（多花成本）与漏报（丢内容）不对称，不得为减少误报而增加漏报。**
   典型形态：为降低命中率而上调阈值、把析取判据改成合取、给闸门加豁免。
   这类改动把**成本错误**换成**内容错误**，方向错误，**不得在未验证的证据上做**。
2. **省成本的改动必须先证明它不降低正确性**；无法证明时，正确的动作是不做，
   而不是「先上再观察」。观察成本由学生承担，不由改动方承担。

**已适用判例**（`source_page_assets.md` §3.2.5，`layout_critical` 的 C5 判据）：
14 页抽样中 `ratio > 2.2` 有 5 个误报、**0 个漏报**。按本原则维持该阈值，
拒绝了「上调阈值躲开行间公式」（会漏掉小插图）与「加合取项减误报」（把成本错误变内容错误）
两种省量改法，代价是继续多付页图 token。

## 七、复审判据：检查读的载体 ≠ 它保证的事实

**独立复审在审查任何新增的自动检查、闸门或验收判据时，必须问一句：**

> **这道检查实际读取的载体，与它声称保证的事实，是不是同一个东西？
> 如果不是，它保证不了那件事。**

该判据来自一日内出现的三个同型缺陷——共同结构是「声明载体便宜、机器可读，实质载体贵或
不可读，而检查只够得到前者」：

| 判例 | 检查读的（声明载体） | 要保证的（实质载体） | 后果 |
|---|---|---|---|
| `P-0058` | `progress.md` frontmatter 指针 | checkpoint 表 | 手写值通过检查，`--check` 连续两次报绿 |
| frontmatter 陷阱（`source_page_assets.md` §3.2.4） | `page_NN.md` 的四个前置（全在 frontmatter） | 页正文 | 四前置全满足而正文一字未投递 |
| `P-0059` | checkpoint 行标 `confirmed` | 实际交付的图形 | 记为已覆盖，三处均无交付痕迹 |

**三例均由人工察觉，无一被任何自动检查发现**——这正是它需要成为复审问题而非新增检查的理由：
一个自查此类错位的元检查，本身依赖每道检查如实申报「自己读什么」，
那是同一个缺陷的又一实例。

**判定为错位时的处置**（择一，不得留空）：
让检查改读实质载体；或为实质载体补生产者使两者合一（`P-0058` 的做法）；
或**在检查旁显式声明它保证不了什么**，不得让调用方误以为已被覆盖
（`source_page_assets.md` §3.2.5 的已知漏报即按此处置，并钉成测试）。
